# Roadmap: Universal Platform Refinement — Governance, Visibility & Scope-Bounding for the AI Video Pipeline

> Land the strategic follow-up to PR #176 in a single PR: make the new video capability visible to non-developers in the README and role-guide, install the missing media-governance + provider-lifecycle + persona-governance rule layer, ship the Python tests the pipeline shipped without, and record a domain-pack-readiness ADR that bounds the platform's future scope without extracting any code in this PR.

## Context

PR #176 (AI Video Pipeline) shipped a complete, governance-aware, dry-run-default video generation system: 5 provider adapters behind a four-method shell contract, 3 personas, 5 skills, the `/video:*` command cluster, a Banana-Arc pixel-similarity regression harness, secret-redaction at every adapter boundary, and 50 roadmap steps completed (22/22 lint clean, 359 tests passing). The strategic review that followed gave the work `8.9 / 10` — engineering `9.7`, governance `9.2`, UX `10`, scope discipline `6.8`. The review's load-bearing critique was not technical: the platform's positioning, role-guide, and rule-layer never caught up to the new capability, and the product-strategy guard-rails that *would* let video coexist with developer / founder / consultant work were never installed.

This roadmap closes that gap **in one PR**. It does not extract a "domain pack", it does not refactor adapter architecture, it does not move any shipped file. It ships the **visibility surface**, the **rule layer**, the **tests the pipeline shipped without**, and the **architectural decision record** that fixes the scope of the platform before the next domain (audio / image / docs / exports) lands. Domain-pack extraction is named, scoped, and explicitly deferred to a separate structural roadmap so that this PR stays lightweight and reviewable.

## Notes

### Why these phases, why this order

The strategic review's load-bearing critique was *scope discipline* (6.8 / 10), not engineering (9.7 / 10). Engineering is already strong; the missing surface is the **rule and policy layer that makes future domains safe to add without enlarging the kernel**. Phase 2 (media-governance) and Phase 3 (provider-lifecycle + persona-governance) install that layer. Phase 1 (visibility) and Phase 5 (advisory issues) close the *outside-of-code* gaps the reviewer named as "three steps, all outside the code". Phase 4 (Python tests) closes the test gap surfaced by the same reviewer. Phase 6 (ADR) records the decision to *not* extract domain packs today — making the deferral auditable rather than implicit, which is the actual cost-of-future-flexibility being bought by this PR.

### Single-PR constraint — discharge plan

If any phase cannot fit in one PR's reviewable budget, the cut is documented here, not split into a follow-up PR. Candidates for cut, in order of acceptable casualty:

1. Phase 5 advisory issues (smallest cost — they remain in the strategic-review trace and can be opened post-merge).
2. Phase 4 Step 4 (adapter-contract test file — the schema + prompt-optimization tests are the load-bearing ones).
3. Phase 3 Step 6 persona-governance linter (rule + docs ship; linter can land as a follow-up commit on `main`).
4. Phase 6 Step 5 ADR council debate (per §Council-debate verdict #5) — ADR can ship at status `proposed` instead of `accepted`; one council pass on the ADR can be deferred to a follow-up commit. The ADR text itself is not a cut candidate; only its second council pass is.

Phases 1, 2 Steps 1–6, 3 Steps 1–5, 4 Steps 1–3, and 6 Steps 1–4 are *not* candidates for cut.

### Domain-pack extraction — explicitly deferred

The `8.9 → 9.6` scoring delta the strategic review argued for *is real*, and the host position is that it is also *not unlocked by extracting today*. The trigger for extraction is named in Phase 6 Step 1: two independent domains with overlapping execution surfaces. The repository currently has one such domain (video). Audio, image, docs, and exports are surfaced as named *future* concerns by the strategic review and by the predecessor roadmap, but none is built. Extracting a one-domain platform produces a pack with no peer to share the abstraction with — the abstraction is structurally premature. The ADR records this reasoning so the deferral is reviewable rather than habitual.

### Council usage in this roadmap

**Convergence note.** After folding R1+R2 findings into this roadmap, a third pass was run against the gefoldete artefact and seeded from R2 to surface any residual gaps. Both members re-emitted their R2 responses byte-identical (Anthropic: 11221 chars match; OpenAI: 2245 chars match) — no new finding, no shift in position. The synthesis is locked.


**Round 1.** Anthropic raised the load-bearing critique: the roadmap proposes a *governance layer* (Phase 2 policies, Phase 3 lifecycle rules) but provides no *Policy Decision Point* — no gating function in the execution path, no machine-checkable schema, no audit log. Cites the shipped `AIV_DRYRUN=true` and adapter-boundary secret-redaction as precedent that "load-bearing constraints live in code, not prose." OpenAI was directionally positive on structure, flagged single-PR risk as the only concern.

**Round 2.** Anthropic rebutted with a category distinction: cost-safety (boolean, automatable) belongs in code; ethical-safety (likeness, public-figure, brand-impersonation — requires LLM judgment) cannot be deterministically gated without an LLM in the loop, which collapses back to agent-mediated enforcement. The platform's contract is agent-in-the-loop, not autonomous gating — the agent's session transcript *is* the audit log. A PolicyEngine module that returns allow/deny is architecturally incompatible with this contract and is over-engineering. OpenAI switched sides and endorsed Anthropic-R1's enforcement-gap framing.

**Host verdict.** Anthropic-R2's category distinction is technically correct: ethical-safety policies are *non-automatable by construction*. The right response is not to ship a PolicyEngine; it is to (a) make the agent-in-the-loop enforcement model explicit so future readers can't misread the policy files as TODOs for a missing gate, and (b) install one small *structural* check that fails CI if a policy exists but is unreachable from any skill — so the policy layer cannot silently rot. The existing refusal-path test in Phase 4 Step 3 already proves the policies are reachable from code; this verdict tightens that proof and makes the model auditable without inventing a new enforcement surface.
