# Roadmap: Leaner core + discovery — close the post-5.x feedback gaps the package can actually act on

> Synthesis of seven external review rounds (feedback 9–15, May 2026) cross-checked against the live tree. Six of those rounds re-praised the same thing (elite architecture / governance / engineering) and re-named the same single risk: **meta-complexity** — "systems over systems" (value systems, roadmap systems, Iron Laws, measurement, linked-projects, marketplace) that each new feature now inherits as a tax. A neutral two-model council (anthropic/claude-opus host + openai/codex + google/gemini, CLI transport, 2026-05-30, analysis lens) was polled on the five genuinely-new, agent-doable candidates distilled from those rounds. **Both external members independently ranked the Meta-System / Abstraction Audit P0 and the single highest-leverage item**; both kept Cross-Repo Retrieval, Marketplace Discovery, and a discoverable BREAKING_CHANGES.md; they split only on Linked-Projects Visualization (codex: keep-P2; gemini: drop as "eye candy") and gemini surfaced one genuinely-missing item the five did not cover — a non-destructive **skill dry-run / preview** for non-dev safety. This roadmap implements that converged verdict in the council's converged sequence: stabilise the core first (audit), then the cheap communication fix, then discovery + retrieval on the leaner foundation, with visualization gated last on the retrieval model proving useful. Everything the feedback asked for that is **already shipped** (semver policy, SSE edge-case tests, value dashboard, employee workspace, role experiences, linked-projects detection) or **deliberately Hard-Floor cancelled** (org-mode, OAuth connectors) is enumerated in Notes so review round 16 does not re-litigate it.

## Context

The package has crossed the line where its own surface area is the dominant product risk — not capability, not quality. Every feedback round from 9 onward says the technical proof is done; the open work is either (a) **outside the code** (recruit sessions, registry claims — human-owner, tracked in the active employee roadmap) or (b) **about the shape of the code itself** (too many meta-layers; 218 skills nobody can navigate; a sibling-repo map that is detected but never used). This roadmap is scoped strictly to (b)-class items the agent can build, validated by an external council so the build list is not one maintainer's taste.

- **Council convergence (2026-05-30, analysis lens, CLI transport):** Meta-System Audit = P0 + highest leverage (both members, independently). Cross-Repo Retrieval = KEEP (codex P1 / gemini P0). Marketplace Discovery = KEEP P1 (both). BREAKING_CHANGES.md = KEEP P1, cheap (both). Linked-Projects Visualization = split (codex keep-P2 / gemini drop) → demoted to gated/optional. Missing-item catch (gemini): skill dry-run / preview mode → adopted as Phase 5.
- **Sequencing (both members):** audit + docs first to stabilise the core, then discovery + retrieval on the leaner foundation, visualization last.
- **Strategic frame:** every phase either *removes* surface (Phase 1) or makes existing surface *reachable / safe* (Phases 3–6) — none adds a new always-loaded abstraction. A phase that would add a new meta-layer fails its own premise and must be descoped.

## Phase 4: Cross-repo retrieval — turn the sibling graph into a read-only context layer (P1)

> Both members KEEP (gemini P0). Builds directly on the ADR-032 detector, which today only produces a passive *awareness note* — this phase makes the detected siblings a **read-only retrieval source** so the agent can pull cross-repo context (an API contract the frontend consumes, a shared type) without bulk-including files. Stays inside ADR-032 **Option A** (passive, read-only, opt-in-per-sibling, no bulk inclusion); does **not** advance to Option B (auto-scan) or C (implicit inclusion). Also closes the ADR-032 open follow-up "expose the detector as a CLI subcommand for consumer reach". Main risk both flagged: retrieval noise / stale context worsening decisions → every retrieved chunk carries its source sibling + path + a freshness stamp, and retrieval is **targeted-query-only**, never a blind sweep.

- [x] **Step 1:** Author `docs/contracts/cross-repo-retrieval.md` — scope (read-only; opt-in `linked_projects[].include: true` siblings only; targeted query, never full-tree sweep), the retrieval envelope (`source_repo`, `path`, `chunk`, `freshness`, `match_reason`), bounds (≤ N chunks per query, large-flagged siblings get targeted-glob-only per the detector's `large` flag), and the Hard-Floor reminder (no writes — out-of-root writes still pass the host permission gate; this surface is read-only).
- [x] **Step 2:** Expose the detector as a CLI subcommand — `agent-config linked-projects:list` (closes the ADR-032 follow-up): prints opted-in siblings with `path · detected_via · large`. Pure wrapper over `scripts/_lib/linked_projects.py` + the `.agent-settings.local.yml` `linked_projects` cascade; no detection logic duplicated.
- [x] **Step 3:** Implement targeted cross-repo retrieval — `scripts/cross_repo_retrieve.py` (≤ 300 LOC): given a query + the opted-in sibling list, run a bounded targeted search (path-glob + content grep, never a full walk; respects the `large` flag by requiring a path scope), return the retrieval envelope. Reuses the chunking + redaction floor from `knowledge_ingest.py` (never surface secrets across repos).
- [x] **Step 4:** Surface as `/knowledge:cross-repo <query>` (command file under `commands/knowledge/cross-repo.md`) — renders matches as `source_repo · path · freshness · why`. Honours opt-out (a sibling not `include: true` is never read). Inert with a clear message when no siblings are opted in.
- [x] **Step 5:** Wire the cross-repo source into `memory_retrieve` as a tagged, **discounted** source (`source: cross-repo`, scored below local curated knowledge, mirroring the 0.85× discount the `knowledge:` namespace already uses) so cross-repo context never outranks the project's own truth. Schema-compliant envelope projection.
- [x] **Step 6:** Coverage — `tests/test_cross_repo_retrieve.py` against fixture sibling repos under `tests/fixtures/cross-repo/`: targeted query returns scoped matches, large-flagged sibling rejects an unscoped query, opt-out sibling is never read, secrets in a sibling are redacted, no-siblings path returns the inert message. No live network, no real cross-repo writes. <!-- carve-out: new-gate-verification -->
- [x] **Step 7:** Author `docs/guides/cross-repo-retrieval.md` and cross-link `docs/guides/cross-repo-linked-projects.md` (the existing detection guide) so detection → retrieval reads as one story.

## Phase 5: Skill dry-run / preview mode (P1)

> The council's missing-item catch (gemini): with 218 skills and high-power commands, non-dev personas need a non-destructive way to preview what a skill/command will mutate before it runs. This is both a safety surface (non-dev confidence) and a discovery surface (see what a recommended skill does before committing). Scoped to **preview**, not a sandbox — it surfaces the planned actions, it does not execute a fenced copy.

- [x] **Step 1:** Author `docs/contracts/skill-dry-run.md` — what "preview" means (the skill's declared steps + the files/commands it would touch, read from its frontmatter + body), the explicit non-goal (NOT a sandboxed execution; NOT a guarantee of side-effect-freeness for skills with `execution` blocks), and the surface (`--preview` flag + `/skill:preview <name>`). Ties to `runtime-safety` (default execution type `manual`; `assisted` must propose, never execute silently).
- [x] **Step 2:** Implement the previewer — `scripts/skill_preview.py` (≤ 250 LOC): parse a skill's SKILL.md, extract declared steps, `allowed_tools`, `execution.handler`, and any file/command targets named in the body; render a plain-language "this skill will: …" summary. For `execution: manual` skills (the default), state "instructional only — no automatic execution".
- [x] **Step 3:** Surface as `/skill:preview <name>` (command file under `commands/skill/preview.md`) — plain-language summary by default (reuses the Phase-6-of-the-employee-roadmap plain-explain tone), with a `--technical` toggle showing the raw frontmatter + step list.
- [x] **Step 4:** Coverage — `tests/test_skill_preview.py` against fixture skills: a manual-execution skill renders "instructional only", an assisted-execution skill renders its proposed actions, a skill with `allowed_tools` lists them, a malformed SKILL.md degrades to a structured error rather than crashing. <!-- carve-out: new-gate-verification -->
- [x] **Step 5:** Author `docs/guides/skill-preview.md` — 2-minute walkthrough pairing `/skills:discover` (Phase 3) → `/skill:preview` (this phase) → run, as the non-dev safe-adoption loop.
