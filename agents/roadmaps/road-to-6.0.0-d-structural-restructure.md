# Road to 6.0.0-D — Structural restructure (the hard break)

> Fourth `road-to-6.0.0-*` roadmap and the **deliberate hard break**. 6.0.0-A/B/C
> made the pack the surfacing/governance unit *in metadata*; this roadmap makes
> the **source tree itself show the product structure**: commands physically
> nested under their pack as `src/domains/<pack>/<verb>/`, skills + rules as one
> flat shared library, root reduced to tool/build essentials + `src/` + `tests/`
> + `taskfiles/`, profiles as curated views. There is **no backward
> compatibility** — a `migrate` command (4→6 and 5→6) plus `MIGRATION.md`
> (linked from the README) carries existing installs across.

> **Why a hard break, by design.** Few users, mostly the maintainer's team. The
> current layout has bothered the maintainer for a long time; spreading the cut
> over many versions is worse than one clean major. This roadmap optimizes for
> the cleanest end-state, not for path stability.

## Branching strategy

> **Integration branch — `refactor/6.0.0`.** Same shared integration branch as
> the other `road-to-6.0.0-*` roadmaps. Every phase branches off it and opens
> its PR against `refactor/6.0.0`. Because this is the largest, most
> path-invasive of the four, it merges **last** into the integration branch;
> only when A+B+C+D are assembled and green does `refactor/6.0.0` merge to
> `main` in one final 6.0.0 integration PR.

## Goal

The repository layout reads as the product: open `src/domains/git/` and see
`commit/` and `pr/`; open `src/skills/` and see the whole reusable building-block
library in one place; run `commands ls --profile developer` and get exactly
`work · review · fix · commit · pr`. Root carries only what tooling and the
agent host require. The cut is a single hard 6.0.0 break with a migration path.

Notes:
- **Skills + rules stay flat and shared** (not duplicated per pack) — easier
  overview and a single namespace so no skill / rule / command can ever collide
  on name. A command references skills by slug; the dependency is declared in the
  pack's `pack.yaml`.
- **`src/domains/<pack>/`** replaces today's flat `commands/` + `pack:`
  frontmatter: the path *is* the ownership.
- **Profiles never hold files** — `developer.yaml` lists the command set it
  surfaces; the curated tree is rendered, not stored.
- **Thin command over skills + scripts (maintainer principle).** A command is a
  THIN base: its `.md` is a short orchestration spec that triggers the needed
  skills + (preferably TS, else py) scripts — heavy logic lives in `src/skills/`
  and scripts, never in the command. When commands merge or are cut, the removed
  pieces become **skills** the survivor composes.
- **Interactivity ENABLES merging (lowest barrier to entry).** A command MAY ask
  ONE short clarifying question to disambiguate instead of splitting into several
  commands — e.g. `fix-pr-comments` detects new bot/human comments and asks which
  to fix, replacing `fix-pr-bot-comments` + `fix-pr-developer-comments`. The
  north star is the smallest visible surface + the easiest entry; a confirm
  prompt is an acceptable merge mechanism (destructive defaults still never
  silent). Concrete merge verdicts live in the worksheet (Phase 4b reference).
- **`_core` vs `engineering-base` vs `git` — no two "core" concepts** (feedback-2):
  - `_core` = the **universal operating surface**, profile-independent: `work`,
    `review`, `fix`, `status`, `help`.
  - `engineering-base` = **engineering capability**: tests, quality, refactor.
  - `git` = its **own domain pack** (`git/commit`, `git/pr`, `git/sync`) — these
    move OUT of `engineering-base` (where 6.0.0-B put `commit`/`create-pr`) into a
    dedicated `git` pack. `commit`/`create-pr` are no longer engineering-base.

## Scope-line rule — 4 categories, 3 lanes (council, 2026-06-03)

> A critical council pass challenged BOTH "defer everything to 6.1" (the external
> feedback) AND "pull everything into 6.0" (the maintainer). The defensible line
> is by change category, not by cost:
>
> | Category | What it is | Lane | Safeguard |
> |---|---|---|---|
> | **Structural** | file moves / renames | **6.0.0** | static analysis + unit tests |
> | **Interface** | new canonical invocation, identical behavior | **6.0.0** | alias + 2-release grace |
> | **Architectural** | new trust boundary / routing-concurrency change | **6.0.x staged** | dual-mode → flip default once routing verifies green |
> | **Behavioral** | detection / runtime change | **6.1** | engineering validation (CI-safety, detection tests) first |
>
> **The rule:** verifiable with static analysis + unit tests → 6.0.0. Needs
> dual-mode staging or detection/CI-safety work → 6.0.x or 6.1. **No 30-day
> telemetry wait** — this package's few/team-internal users mean the maintainer
> knows the usage directly; telemetry corroborates, it never gates. The
> "we touch the files anyway" argument is valid for structural/interface, **invalid
> for architectural** — cost savings never justify an unvalidated trust-boundary
> change. This is how 6.0 takes the MAX safe scope (more than "defer all") without
> becoming a risky all-at-once rebuild.

## Future architecture & consolidation (6.0.x staged + 6.1)

> Recorded so the next lanes are pre-planned. The AI council deliberately did NOT
> rubber-stamp the design — it returned "do not greenlight V6 as-is" with this
> staged path. 6.0.0 is the structural+interface break; the items below are
> 6.0.x (architectural, dual-mode) or 6.1 (behavioral).

- **6.0.x staged (architectural, dual-mode) — runs in the 6.0 patch line, NOT
  deferred to 6.1.** It's architecture, not a user feature, so it needs no usage
  data — only a static green check.
  - **Meta-pack split** (`meta` → `agent-admin` / `memory` / `analytics` /
    `governance`). The maintainer's lean: do it **as soon as the dependency gate
    is green**, in 6.0.x. The gate is exactly the **Phase-0 dependency + pack-graph
    lint** (already built in this roadmap): once it shows `meta`'s sub-areas have
    zero cross-pack dependencies, split them into real packs (dual-mode: a virtual
    `meta` keeps resolving for back-compat, flipped/removed in a later patch). No
    telemetry, no 6.1 wait — `meta` is already, by our own admission,
    agent-admin + memory + analytics + governance.
  - **Orchestrator-head folding completion.** Dual-mode ships in 6.0.0
    (Step 13); flip the default + remove legacy in 6.0.x once routing verifies
    green.

- **Interactive-merge contract (gate for every merge in 6.1).** A merged command
  (`fix-pr-comments` ← bot/human, `analytics` ← show/prune, `tests` ← create/run,
  conditionally `judge`/`override`) MAY ask one short question — but MUST work
  non-interactively: detect a non-TTY (CI), honor `--yes`/`--json`/explicit
  flags, and fall back to a safe default without hanging. Council: interactive
  prompts that block CI are "provably wrong for CI/CD". No merge ships without
  this escape.
- **Framework-neutral / stack-adaptive commands — APPROVED, scoped to
  engineering** (resolved: "yes, worth it — but only engineering"). The
  stack-adaptive set is `test-run`, `test-create`, `quality-fix`,
  `review-changes`, `work`. A resolver DETECTS the toolchain (phpunit / pest /
  playwright / vitest / jest / …) and runs the right one — NO per-stack command
  explosion (`php-test-run`/`jest-test-run` is the bad world). Monorepo guard:
  default to FAST tests, `--include-slow`/`--include-e2e` opt-in. Per-stack
  commands captured in an auto-generated project config. Only genuine PHP-space
  commands stay PHP-locked.
- **KILL list (delete, not merge).** Separate `security`/`performance` review
  commands (fold into `review` lenses), stack-variant command duplicates,
  low-usage system-introspection (`skill-preview`, `skills-discover`,
  `review-routing`, `rule-compliance-audit`) → behind `agents-audit` /
  `agent-admin`, not top-level.
- **Meta-pack split.** `meta` is several products (memory, council, analytics,
  context, override, profile, agents, governance). Split into `agent-admin` /
  `memory` / `analytics` / `governance` (feedback-3).
- **Flows layer (the biggest post-break improvement, feedback-3).** Make the
  implicit flow explicit: `Profile → Pack → Flow → Command → Skill → Rule`. A
  Flow names a multi-command journey (e.g. "implementation flow" = ticket-implement
  · work · feature-dev). Spec it as its own architecture roadmap.
- **`future_state` worksheet axis.** Each command's intended end-state
  (command / skill / alias / remove) is annotated in
  `agents/reports/command-classification-6.0.0-d.md`; it drives the 6.1 cut.
- **Day-one experience — RESOLVED.** Profiles are internal, never sold as a
  day-one concept. Wizard/CLI asks "What are you doing?" (Software Development /
  Product & Roadmaps / Content Creation / Finance & Planning) → maps to a profile
  id; Simple (default) vs Advanced toggle. The first-5-minutes flow shows what
  was detected (`/test → Jest, 23 files found`) with error recovery.
- **Routing/activation telemetry — APPROVED, NOT product analytics** (resolved).
  Collect only the gold metrics: `command · intent · pack · activated skills ·
  activated rules · duration · success/abort`. Never "user clicked X". This is
  the data 6.1 prunes on (a never-routed skill → remove; an internal-only command
  → `internal`; a 90%-used command → promote). Extends the existing local-only,
  opt-out analytics surface (6.0.0-C), never POSTed.
- **Flows are the real 6.1 theme.** Per the reviewer: after the structural break,
  the next discussion is "what are the 5 most important product Flows?" — not more
  command/skill debates. Make Flows the headline of the 6.1 architecture roadmap.
