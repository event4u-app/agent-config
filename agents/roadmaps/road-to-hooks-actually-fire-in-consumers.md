# Roadmap: Hooks actually fire in consumer projects — close the marketplace-install gap

> Triggered by a concrete failure observed on **2026-05-29** in the sibling consumer project `event4u/agent-ide-plugin` (branch `feat/road-to-phase-0-validation`, commits `46d3d8b`, `c3b806e`). The `roadmap-progress-sync` rule's Iron Law mandates a dashboard regen on every roadmap touch — but the dashboard there only updated when a human manually ran the regenerator and committed it. No `SessionStart` / `PostToolUse` hook ever fired. This roadmap fixes the **plugin-side** install + dispatch path so hooks land and run in any consumer that enables the marketplace plugin, regardless of whether `agent-config init` was ever run locally.

A Council pre-check (`agents/runtime/council/responses/hooks-actually-fire-roadmap-precheck.json`, 2026-05-29, anthropic/claude-sonnet-4-5 + openai/gpt-4o, 2 rounds, $0.09 actual) cross-checked this structure. Seven accepted findings folded inline below: **phases reordered** (Phase 4 now precedes Phase 3 because `--regen` depends on the pinned canonical path); dispatch-issues log cap raised 50 → 200; first-run banner gains a `.augment/.first-run-action-needed.md` file alongside the stderr line; explicit JSONL schema; setup-complete detector to avoid banner spam; explicit Phase 6 fixture strategy (plugin-side completeness ≠ consumer-side readiness); `--lifecycle` alias for the `--claude` flag.

## Context

### Symptom — what the consumer saw

Consumer project: `/Users/mathiasberg/projects/galawork/galawork-packages/event4u/agent-ide-plugin`

- `agents/roadmaps/road-to-phase-0-validation.md` flipped from 0 → 20 done checkboxes across multiple commits.
- `agents/roadmaps-progress.md` updated **only** when the author manually invoked the regenerator and committed. Two such commits exist (`46d3d8b`, `c3b806e`); zero hook-driven regens.
- Iron Law in `roadmap-progress-sync.md` ("roadmap touch → regenerate the dashboard, same response") is structurally un-enforceable in this consumer.

### Root-cause inventory — what's missing in the consumer

| Artefact | Expected location (consumer) | Present? | Effect when missing |
|---|---|---|---|
| `.claude/settings.json` with `enabledPlugins.agent-config@event4u-agent-config: true` | `.claude/settings.json` | **no** | Claude Code never loads the plugin → `hooks/hooks.json` never reached |
| `./agent-config` symlink → `scripts/agent-config` | repo root | **no** | Even if hooks fire, every `"$CLAUDE_PROJECT_DIR"/agent-config dispatch:hook` command errors `command not found` |
| `update_roadmap_progress.py` regenerator | one of: `.augment/scripts/`, `.agent-src/scripts/`, `.agent-src.uncondensed/scripts/` | **no** | `roadmap_progress_hook.py::_resolve_regenerator` returns `None`, hook silently no-ops |
| `.git/hooks/pre-commit` (from `agent-config hooks:install`) | `.git/hooks/pre-commit` | **no** | No backstop on the dashboard at commit time |
| Hook-dispatch logs / state file under `agents/runtime/state/` | `agents/runtime/state/roadmap-progress.json` etc. | **no** | No observable evidence that hooks ever ran |

The consumer enabled the plugin path implicitly (the repository even ships `agents/roadmaps-progress.md` with the comment "Auto-generated by `.augment/scripts/update_roadmap_progress.py`" — but that script is not in the repo) without running `agent-config init`. The marketplace-install path (`/plugin install agent-config@event4u-agent-config`) is silent on these prerequisites.

### Why this is a plugin bug, not a consumer bug

1. **Marketplace install ≠ `agent-config init`.** The `.claude-plugin/marketplace.json` plugin entry ships `hooks/hooks.json` and the `agent-config@event4u-agent-config` plugin id. A user who enables the plugin via `/plugin install` gets the *hooks* but **none** of the prerequisites those hooks require (`./agent-config` symlink, `update_roadmap_progress.py`, the runtime state dir). The hooks fire under Claude's lifecycle, `dispatch:hook` runs through the resolved `$CLAUDE_PROJECT_DIR/agent-config` — which does not exist — and the hook system exits silently per its never-block contract.
2. **`dispatch:hook` has no self-diagnostic surface.** Every concern hook (`roadmap_progress_hook.py`, `chat_history.py`, `verify_before_complete_hook.py`, …) is wired to swallow `OSError`/`SubprocessError` so the agent loop never breaks. That contract is correct — but the consumer has no way to *see* that hooks tried-and-failed.
3. **`hooks:install` covers only the git pre-commit gate**, not the Claude Code lifecycle wiring. There is no single command a marketplace user can run to repair "the plugin is enabled but its scaffolding is missing".
4. **The regenerator is referenced from three speculative paths** in `roadmap_progress_hook.py` lines 100-107. None ship by default. The contract is fork-then-pray.

### Gates

- `minimal-safe-diff` — every edit lands in a file directly named below. No drive-by refactors of `install.py` or `condense.py` beyond what each phase calls out.
- `scope-control` — no new CLI subcommands beyond the ones each phase enumerates. No tag/version steps; roadmap plans work.
- `roadmap-progress-sync` — flip checkboxes inline as steps land; regen the dashboard.
- `verify-before-complete` — each phase ends with a concrete probe command + expected output.
- `quality.local_auto_run = false` policy — new gates introduced *by this roadmap* may run once locally with the `<!-- carve-out: new-gate-verification -->` marker; existing CI pipelines stay remote-only.

### Non-goals

- Re-architecting the universal dispatcher (`scripts/hooks/dispatch_hook.py`). It works; the failure is upstream of it.
- Touching other consumer projects. The failing project is the *witness*; the fix lands in the package.
- Replacing the marketplace install path. Users who run `agent-config init` locally already get a working setup — that path is the reference.

## Phase 1: Make `dispatch:hook` observable when prerequisites are missing

The Iron Law in the hook architecture says hooks never block the agent. The *user-facing* corollary is missing — when a hook can't run, the user must be able to discover that fact without running `hooks:doctor` manually.

- [ ] **Step 1:** Edit `scripts/hooks/dispatch_hook.py` — when a concern's resolver returns `None` (script missing, regenerator missing, `./agent-config` symlink missing in `$CLAUDE_PROJECT_DIR`), append a single JSON line to `agents/runtime/state/dispatch-issues.jsonl`. **Schema (locked by Council R3 pre-check):** `{"timestamp": "<ISO-8601 UTC>", "hook": "<concern-id>", "issue": "<enum: prerequisite_missing | script_not_found | permission_denied | execution_failed>", "detail": "<freeform>", "resolution": "<one-line command or doc link>"}`. Bounded log: rotate at **200 entries** (council-revised from 50; debug sessions with many tool calls would have lost evidence at the old cap); drop the oldest.
- [ ] **Step 2:** Edit `scripts/hooks_doctor.py` — read the new `dispatch-issues.jsonl`, surface the last N entries grouped by concern in the existing report sections. Add a one-line CTA at the top of the report when entries exist: "Hooks tried to fire but couldn't — run `./agent-config init` (or follow the per-concern hints below)".
- [ ] **Step 3:** Edit `scripts/roadmap_progress_hook.py::_resolve_regenerator` — on the `return None` path, write the dispatch-issue line directly (the hook is invoked as a subprocess from the universal dispatcher; routing the write through the dispatcher adds latency for no benefit). Keep the `verbose` stderr line unchanged.
- [ ] **Step 4:** Add `tests/hooks/test_dispatch_issue_log.py` — fixture: dispatcher invoked with a payload that targets a missing-script concern. Assert `dispatch-issues.jsonl` grows by one entry with the expected schema. <!-- carve-out: new-gate-verification -->
- [ ] **Step 5:** Run the new test once locally to satisfy `verify-before-complete`: `python3 -m pytest tests/hooks/test_dispatch_issue_log.py -x`. Confirm green. <!-- carve-out: new-gate-verification -->

**Exit criteria:** any hook firing in a non-installed consumer leaves a trace under `agents/runtime/state/dispatch-issues.jsonl`; `hooks:doctor` surfaces it; the new test is green.

**Rollback:** revert the four scripts and delete the test.

## Phase 2: First-run banner when the plugin is enabled but unscaffolded

A marketplace-install user has no UI surface to discover the missing prerequisites until something tries to run. The `SessionStart` hook is the right surface — it fires before the user types.

- [ ] **Step 1:** Add `scripts/first_run_gate_hook.py` — runs on `session_start` only. Detects the failure shape: `$CLAUDE_PROJECT_DIR/.claude/settings.json` contains `enabledPlugins.agent-config@event4u-agent-config = true` **AND** (`$CLAUDE_PROJECT_DIR/agent-config` is not executable **OR** none of the three `update_roadmap_progress.py` search paths exist). Output one line on stderr (Claude shows it in the lifecycle log) **AND** write `$CLAUDE_PROJECT_DIR/.augment/.first-run-action-needed.md` (Council R3 HIGH — stderr alone is invisible to the average user; the file makes it discoverable on `ls`). **Setup-complete detector (Council R3 MEDIUM):** exit early without writing if `.augment/.first-run-action-needed.md` does not exist AND the setup checklist passes (`./agent-config` symlink executable + `.augment/scripts/update_roadmap_progress.py` exists) — prevents banner spam after successful `--claude --regen` run.
- [ ] **Step 2:** Wire the new concern into `scripts/hook_manifest.yaml` — add `first-run-gate` under `concerns:` (fail_closed: false), and add it to every platform's `session_start` array (claude, cowork, cursor, cline, windsurf, augment, gemini, copilot — each platform's session_start line).
- [ ] **Step 3:** Edit `scripts/lint_hook_manifest.py` to recognise the new concern (the linter parses the manifest and asserts concern names match a known set).
- [ ] **Step 4:** Update the `agent-config hooks:doctor` snapshot in `tests/hooks/test_hooks_doctor_snapshot.py` to include the `first-run-gate` row. <!-- carve-out: new-gate-verification -->
- [ ] **Step 5:** Add `tests/hooks/test_first_run_gate.py` — fixture A (plugin enabled + no scaffolding) → stderr line written; fixture B (plugin enabled + symlink present + regenerator present) → silent; fixture C (plugin not enabled) → silent. Run once locally. <!-- carve-out: new-gate-verification -->

**Exit criteria:** a fresh consumer that only ran `/plugin install` sees one stderr line on session start naming the missing artefacts and the fix command. No false positives on a properly-`init`'d consumer.

**Rollback:** delete `first_run_gate_hook.py`, revert the manifest, linter, and tests.

## Phase 3: Pin the regenerator distribution path

> **Reordered before the original Phase 3 (`hooks:install --claude`) per Council R3 HIGH:** Phase 4's `--regen` flag depends on a single canonical regenerator path being defined first. Doing the pinning here means the install flag in the next phase has one path to copy, not three speculative ones.

`roadmap_progress_hook.py::_resolve_regenerator` searches three locations. Two of them (`.agent-src/`, `.agent-src.uncondensed/`) only populate in source-checkouts of the package itself, not in consumer installs. The hook silently relies on whichever one happens to exist. Pin the contract.

- [ ] **Step 1:** Decide the canonical consumer path. Recommendation (record the decision in this step's checkbox commit): `.augment/scripts/update_roadmap_progress.py`. Rationale — the file is already referenced under that name in the `agents/roadmaps-progress.md` auto-generated comment block, and `install.py`'s existing tool projection lays down `.augment/` already.
- [ ] **Step 2:** Add `scripts/update_roadmap_progress.py` as the canonical source in the package (if it currently lives only under `.agent-src/`, copy it to `scripts/` and add a redirect from the old location). Update `scripts/install.py` to copy the script into `$CONSUMER_ROOT/.augment/scripts/` during `init`.
- [ ] **Step 3:** Edit `scripts/roadmap_progress_hook.py::_resolve_regenerator` — keep all three search paths but order them so the canonical one is first, and on `return None` write a dispatch-issue (Phase 1 § Step 3 hook).
- [ ] **Step 4:** Add `tests/install/test_regenerator_lands_in_consumer.py` — fixture: run `install.py` against a temp dir, assert `.augment/scripts/update_roadmap_progress.py` exists and is executable. Run once locally. <!-- carve-out: new-gate-verification -->
- [ ] **Step 5:** Update `docs/contracts/hook-architecture-v1.md` § "regenerator location" with the pinned decision. If no such section exists, append one.

**Exit criteria:** every fresh `agent-config init` lands the regenerator at `.augment/scripts/update_roadmap_progress.py`; the hook resolves it without falling through; the contract is documented.

**Rollback:** revert `install.py`, the regenerator copy, and the contract doc edit.

## Phase 6: Lint guardrail against re-introduction of the gap

Future maintainers must not be able to ship a marketplace-install path that strands the hooks again.

- [ ] **Step 1:** Add `scripts/lint_marketplace_install_completeness.py` — given the package's `.claude-plugin/marketplace.json` and `hooks/hooks.json`, assert that every dispatcher subcommand referenced by a hook's command line resolves to a real subcommand in `scripts/_dispatch.bash`. **Scope (Council R3 MEDIUM):** plugin-side completeness — the linter checks the PACKAGE ships a valid hooks.json + every command resolves to a real dispatcher subcommand. It does NOT check consumer-side scaffolding (that's the runtime dispatch-issues log's job from Phase 1). This distinction prevents false-positives on "valid plugin + unscaffolded consumer" states.
- [ ] **Step 2:** Wire the linter into the package's existing fast-lint cadence (whichever target runs on PR — recommend the same one that runs `lint_hook_manifest.py`). Targeted command, not full pipeline, per `roadmap-ci-steps-policy`.

Linter MUST PASS — the plugin side is complete, consumer side is a separate concern. **`marketplace_install_broken/`**: hooks.json references `dispatch:hook roadmap-progress-TYPO` (subcommand doesn't exist in `_dispatch.bash`). Linter MUST FAIL with reason `unknown_dispatcher_subcommand: roadmap-progress-TYPO`. <!-- carve-out: new-gate-verification -->

## Notes

- **Witness consumer.** The diagnosis used `event4u/agent-ide-plugin` on branch `feat/road-to-phase-0-validation` (commits `46d3d8b`, `c3b806e`). The state file linked above pins this in evidence.
- **Iron Law restated.** `roadmap-progress-sync` says the dashboard regenerates *in the same response* as a roadmap touch. The plugin currently makes that impossible in marketplace-install consumers. This roadmap closes the gap structurally; per-conversation agent discipline is the fallback, not the primary mechanism.
- **No version / tag steps.** Roadmaps plan work.
- **Cloud surface caveat.** The cowork/cloud platforms in `hook_manifest.yaml` carry an upstream caveat (lifecycle hooks ignored — see `chat-history-platform-hooks.md § Cowork`). Phase 2's first-run banner inherits that caveat — on cloud surfaces it will not fire even after this roadmap lands. Out of scope; tracked in the manifest's comment block.
- **Why no `agent-config init` "auto-run" on plugin-enable.** Considered and rejected: silently mutating the consumer's filesystem when a plugin is enabled violates the non-destructive-by-default Hard Floor. The session-start banner (Phase 2) is the right surface — it tells the user, they decide.
