# Road to a worktree that boots ready

> **Source:** the owner's session retrospective of 2026-11-21 (~380 Claude Code
> sessions across seven repositories), measure 14 of its P1 list — worktree
> bootstrap: clone `node_modules` so the hook bundle is not inflated, fix the
> stale-but-fresh `dispatch.js` heal, provision `.env` without the agent reading
> it, and the PHP-consumer `.tmp/` / vendor / `APP_LOCALE` stand-up pattern as a
> generated per-repo recipe. AI council round of the same day (members anthropic
> and openai, one round, analysis mode): measure 14 drew no criticism from
> either member; anthropic listed it among the measures ready for a roadmap now.
> Owner constraint of the same day: no hand-maintained or owner-written context
> file — every piece of project knowledge here is generated by a command from
> the repository, never authored.

## Goal

A worktree created by `/worktree:create`, by a host-native primitive, or by
hand reaches a green gate run after ONE command, `agent-config
worktree:bootstrap`, with no symlinked dependency tree, no heal that trusts a
touched bundle, no `.env` value in the conversation, and a stand-up recipe the
command derived from the repository rather than one a person wrote.

**Retro evidence (transcript-level, not tree facts):** the PHP API consumer
needed its worktree under a bind-mounted `.tmp/` so the container sees it,
`vendor` linked when `composer.lock` matched, three env files copied by the
owner, `DUMP_DB_HOST` set to the compose service name inside the container,
and a local `APP_LOCALE=en` that overrode the test config and turned two tests
falsely red in three sessions. In this repository the stale bundle was
rebuilt by hand in at least four sessions.

(container memory, cache-tag rules, domain maps) belongs to the retro's
