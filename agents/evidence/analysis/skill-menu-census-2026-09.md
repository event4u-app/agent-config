# Skill menu census — every skill, and what can reach it

Pinned to commit `f1d5f3f3adebc67844d5aee845f9cfb657e6c17b`. Generated by `./scripts-run src/scripts/report_skill_menu_census --emit --pin f1d5f3f3adebc67844d5aee845f9cfb657e6c17b`;
re-running it at the same pin over the same tree is byte-identical, which is what
`road-to-skill-menu-economy` step 1.1 asks to be checkable.

## The rule this census applied

**Commands.** A `src/domains/**/command.md` file counts as reaching a skill when it
references it in one of three disambiguating shapes — `skill:<name>`, a `skills/<name>`
path, or the bare name in backticks. A plain word-boundary match is NOT used: names
like `security`, `database` and `docker` are ordinary English and would hit on every
prose mention. The `skill:<name>` shape is closed with a negative lookahead rather
than a word boundary: `\b` sits between `w` and `-`, so `skill:code-review-lens` was a
hit for `code-review` and a skill would have inherited a longer sibling's references.
Tightening it moved no figure in this corpus, which is recorded rather than assumed.

**Flows.** A `src/flows/*.yaml` file counts when its own `skills:` list names the skill.
Flows carry YAML name lists rather than the shapes above, so applying the command regex
to them returned `flow_refs = 0` for all 299 skills on the first pass. That was a false
zero, corrected before publication; a bare name is safe here precisely because the
`skills:` key bounds where it may be read.

**Menu.** `menu_present` is true unless the frontmatter carries `user-invocable: false`
or `disable-model-invocation: true`.

| Class | Meaning |
|---|---|
| `both` | reachable from a command AND from a flow |
| `command-only` | a command references it; no flow does |
| `flow-only` | a flow references it; no command does |
| `model-routed` | neither, and it is on the menu — the menu is the only entry path this tree can point at |
| `orphan` | neither, and it is off the menu: nothing here reaches it |

## What this census does NOT establish

It does not decide **sole entry path**. A command reference proves a command CAN
reach the skill; nothing here proves the menu never does. `command-only` and
`flow-only` are therefore CANDIDATES for `user-invocable: false` and never the
marking decision — the roadmap's Risk 1 is exactly this misclassification, and its
stated mitigation is a successful command invocation per marked skill, which is a
step 1.2 obligation and not something a static scan can discharge.

An `orphan` row is a question, not a deletion list (K3).
