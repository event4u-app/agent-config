# Council — design of the advisories, security-fix and worktree-cleanup run (2026-10-21)

AI council, `anthropic` + `openai`, CLI seats, one round, 2/2 present, $0.00. Question: `advisories-worktree-run-design-20261021.question.md` beside this file.

## Convergence

| Q | Verdict | Both seats |
|---|---|---|
| Q1 | (a) synchronous, budgeted, once a day on the existing `session_start` handler, gated on a user-owned `worktrees.cleanup: auto` — **declared as an authority expansion** | yes |
| Q2 | (b) `ask` everywhere until the user answers; persisted once (ADR-291) | yes |
| Q3 | (a) refresh from the CLI and an opt-in CI schedule only; `session_start` reads the cache. The read-only notice needs an explicit, narrow council approval before it ships | yes |
| Q4 | (a) native audits + OSV for public packages + endoflife.date; no authenticated GitHub access in v1. Conditional: what the native audits transmit is stated, not assumed | yes |
| Q5 | (a) deterministic helpers with fixture tests; the package-manager mutations stay in the agent session | yes |

## Hardening both seats required (Q6)

- Lock per repository; re-check every predicate (merge proof, clean, ignored files, liveness) immediately before each `git worktree remove`; fail closed on a timeout or an incomplete scan.
- A hard budget means subprocess deadlines, not elapsed-time checks between candidates; a timed-out pass cannot continue after the hook returns.
- Fair traversal across days, so one expensive candidate cannot starve the rest.
- A record per candidate of why it was removed or kept.
- The regenerable-ignored policy is conservative: a minimal built-in set, the rest owned by the repository; ambiguity blocks removal.

## Split

The built-in regenerable set: one seat listed node_modules, vendor, .next, dist, .turbo; the other asked for an empty default and repository-owned configuration only. Resolved by the agent toward the stricter reading (D6 in the worktree roadmap): only paths that are never hand-edited are built in; everything else must be declared generated by the repository's own `.gitignore` comment.

## My answers

**Q1: (a) — Acceptable, but must be declared as an authority expansion.**

Synchronous daily cleanup in `session_start` IS an action (which F2 concerns rejected), but it's legitimate here because:
- Explicitly requested by owner (F1: "automatically where possible")
- Properly gated on user-owned `worktrees.cleanup: auto` (F2d ✓)
- Follows retro precedent for timing/budget (F3 ✓)
- Acts only on proven-safe set with conservative guards

Critical distinction: F2 refused *unsolicited* autonomous actions. This is *solicited* by F1. But per F2(b), it must be **declared as an authority expansion** — the gate is proper declaration + user control, not prohibition.

---

**Q2: (b) — `ask` everywhere until answered.**

Automatic deletion requires explicit consent, even with strong safeguards. The cost of asking once is low; the cost of recovering deleted work is infinite. Users who skim prompts won't realize cleanup is happening if `auto` is default. Opt-in is the right baseline for destructive operations.

---

**Q3: (a) for architecture; wait for blocker resolution before shipping the notice.**

CLI/CI-only refresh + cached read satisfies F4 (no network in hook) and F2(c) (read-only notice). The notice riding the existing handler is architecturally sound. However, the open blocker `concerns-refused-as-authority-expansion` covers session-start notices — even if advisory notices are technically *different* from update notices, the blocker should be formally resolved or explicitly amended before shipping. Conservative closure beats administrative bypass.

---

**Q4: (a) — Native audits + OSV + endoflife.date.**

Well-defined public sources with no auth complexity. GitHub Dependabot (b) adds credential management, API pagination, and bundle pressure (F4) when the ceiling is tight. Ship proven minimal sources in v1; add Dependabot later as opt-in.

---

**Q5: (a) — Deterministic helpers + skill procedure.**

The agent stays in the loop for judgment (test interpretation, risk assessment, mitigation choice) while verified TypeScript handles decidable routing/ledger/PR-building. A CLI engine (b) that autonomously runs package managers creates authority questions the guided path avoids.

---

**Q6: Two safety issues:**

1. **The ignored-file allowlist (F5) must be extremely conservative.** Since `git worktree remove` silently deletes ignored files, only obviously-regenerable paths should be listed: `node_modules/`, `vendor/`, `.next/`, `dist/`, `.turbo/`, lockfiles. Any other ignored file — configs, local scripts, anything ambiguous — must block removal. Document this allowlist prominently in code and output. Better to under-delete than lose work.

2. **TOCTOU race between check and remove.** A worktree can become live, acquire valuable ignored content, or spawn a session after proof but before removal. Mitigation:
   - Lock per-repository during cleanup
   - Revalidate ALL predicates (liveness, dirty state, ignored files, commit integration) immediately before `git worktree remove`
   - Fail closed on ambiguous liveness or incomplete scans
   - Record why each candidate was removed or retained (audit trail)

Additional: what happens if the 3s budget is exceeded? Partial run must be fair across days (don't starve later candidates because first one is expensive).

### openai

Matze, my assessment is **mixed**. The architecture is mostly sound, but destructive cleanup needs explicit consent and last-moment revalidation; governance cannot be bypassed merely by reusing an existing hook handler.

## Answers

**Q1 — (a).** Adding deletion to `session_start` is an authority expansion, but it can be legitimately authorized by an explicit user-owned `worktrees.cleanup: auto` choice and F1. Synchronous bounded execution is preferable to a detached process, provided every predicate is revalidated immediately before removal and cleanup is serialized per repository.

**Q2 — (b).** Default to `ask` until the user explicitly chooses; installation alone is not consent to delete worktrees. Persist the answer once under ADR-291.

**Q3 — (a), and wait for formal blocker resolution.** CLI/CI refresh with cache-only session notices is the correct architecture, but “riding the existing handler” does not determine whether something is a new governed concern. Obtain a short council amendment explicitly approving this read-only, user-gated notice before shipping it.

**Q4 — (a), conditionally.** Native audits, OSV for confirmed-public packages, and lifecycle data provide useful coverage without authenticated GitHub access. However, first prove with fixture/proxy tests that native audit commands do not transmit private package names or dependency metadata contrary to the stated privacy invariant; otherwise the proposed choices are incomplete.

**Q5 — (a).** Deterministic helpers make safety-critical decisions testable while package-manager mutations remain visible inside the user-directed agent session. A standalone execution engine creates unnecessary authority, recovery, and lifecycle complexity.

**Q6 — The check-to-remove boundary is unsafe unless hardened.** The implementation must lock per repository, re-check merge evidence, cleanliness, ignored files, and liveness immediately before removal, and fail closed on timeouts, incomplete scans, or ambiguous state. Also, a “hard ≤3 s budget” requires subprocess deadlines—not merely checking elapsed time between candidates.

## Prior-round assessment

I agree with:

- **Reviewer A:** Q1(a), Q3(a)’s cache architecture, Q4(a), and Q5(a).
- **Reviewer B:** explicit consent in Q2(b), synchronous rather than detached cleanup, TOCTOU protection, repository locking, fail-closed behavior, audit records, and fair traversal across daily runs.
- **Both reviewers:** authenticated Dependabot access should not be part of the first adapter set.

I disagree with:

- **Reviewer A’s claim that Q1 is not an authority expansion.** Moving from observation to automatic deletion is plainly an expansion of authority. The explicit `auto` setting can authorize that expansion; it does not make the expansion disappear.
- **Reviewer A’s assertion that the advisory notice may ship merely because it uses an existing handler.** Handler reuse is an implementation detail, whereas a governed concern is defined by behavior and authority. With a directly relevant blocker still open, formal closure is the cleaner and safer course.
- **Reviewer A’s proposed regenerable examples.** Broad entries such as `dist/`, `.next/`, or possibly `vendor/` may contain locally valuable outputs, patched dependencies, or diagnostic artifacts. “Usually generated” is insufficient grounds for deletion.
- **Reviewer B’s wording that the open blocker explicitly covers this advisory notice.** The facts identify the blocker with the update-notice concern, not necessarily this new advisory notice. Nevertheless, the precedent is close enough that an explicit amendment is warranted.

## New refinements

- Treat the regenerable-path policy as repository-owned configuration rather than a universal built-in list. The safest default is an empty allowlist.
- Define “live” using a lease or heartbeat with PID-reuse and stale-marker handling; a bare marker file is inadequate.
- Make proof and removal candidate-specific and emit structured reason codes for every retained or removed worktree.
- Ensure a timed-out removal cannot continue after the hook returns.
- Test native audit traffic against a controlled endpoint. The assertion that “private package names are never sent” must cover package-manager behavior, not only custom adapters.
- Distinguish vulnerability freshness from cache freshness in the session notice so stale cache data cannot look current.

The strongest argument is that **authority, implementation location, and safety are separate questions**: an existing handler may host the work, but deletion still needs explicit authorization and race-resistant execution.

The strongest counter-argument is that one-time consent and another council check add friction to a deliberately 30-second product. That cost is justified for deletion, while the council amendment can be narrowly scoped and resolved without expanding the onboarding wedge.

Concrete next steps: select **Q1(a), Q2(b), Q3(a), Q4(a) conditionally, and Q5(a)**; formally clear the advisory-notice governance question; then require locking, immediate revalidation, subprocess deadlines, privacy traffic tests, and an empty-by-default regenerable allowlist before enabling automatic cleanup.

**Summary:** Proceed with the bounded designs, but require explicit cleanup consent, formal notice approval, race-safe removal, and verified private-package handling.
