# Two open owner decisions on autonomous roadmap runs — the owner delegates both to this council

You are an independent reviewer for the `event4u/agent-config` repository, a governed suite of
rules, skills and commands for AI coding agents. The repository owner has explicitly handed both
decisions below to this council (2026-11-03): "decide both questions in the AI council". Give a
verdict on each, independently. For each: choose one option (or a better-specified variant), give
the reason, the main risk, whether it is reversible, and the concrete wording or rule you would
write.

## Facts from the current tree

- `/roadmap:process-full` runs a whole roadmap end-to-end. Since ADR-237 the invocation itself is
  the confirmation: no acceptance screen, no mid-run approval requests; the final PR is the
  interaction boundary. Only five halt conditions stop a run (Hard Floor, council-off plus genuine
  ambiguity, security-sensitive surface, scope-out-of-roadmap work, test/quality red past the
  fix-loop bound). As of 2026-11-03, `process-step` and `process-phase` use the same grant model,
  differing only in scope.
- The owner has reported three times (2026-10-19, 2026-10-22, 2026-11-03) that runs stop early or
  ask questions mid-run, and asked for runs that finish without interruptions.
- Two run-level fields exist in the execution contract:
  - `late_artifacts`: `halt` (default) stops the run at an artifact the plan did not name;
    `auto-research` re-runs the overlap research mid-run and continues, capped at three such
    discoveries per run.
  - `deferred_policy`: `wait` (default) keeps a synchronous prompt at closure when deferred `[~]`
    items remain; `spawn-follow-up-draft` creates a follow-up roadmap carrying each deferred item
    and its blocker, automatically. A third value, `cancel-with-memo`, drops an item and stays
    owner-decided either way.
  The defaults were chosen by a two-seat council on 2026-08-20 with the reasoning "the aggressive
  path becomes a thing a run declares rather than a thing it inherits", at a time when every run
  had a screen to declare it on. `process-full` no longer has a screen. Since 2026-11-03 the
  invocation flags `--late-artifacts auto-research` and `--deferred spawn-follow-up-draft` can
  declare them.
- A repository rule says decisions classified `high_impact` or `user_required` "always reach the
  user". The execution contract says these classes "escalate during the run, at the moment they
  fire". `process-full` says the owner is never interrupted mid-run for a decision the invocation
  delegated. A separate repository rule, "ask before park", says a decision only the user can make
  is put to the user before a step is parked as blocked, on an interactive host.
- On 2026-11-03 the same council split on O-1 (one seat: flags only; the other: process-full gets
  its own aggressive defaults) and called O-2 a policy decision outside its remit. The owner has
  now explicitly delegated both.

## O-1 — process-full's default run-level policy

- (a) Keep `halt` / `wait` as process-full defaults; the flags remain the way to opt in.
- (b) process-full defaults to `auto-research` (cap 3 unchanged) and `spawn-follow-up-draft`; the
  other commands keep `halt` / `wait`; a flag can still set the conservative values.
- (c) Another shape (state it).

## O-2 — `high_impact` / `user_required` decisions under process-full

Does a decision of these classes count as having "reached the user" when it is recorded in the
final PR body instead of being asked mid-run?

- (a) No: these still interrupt the run at the moment they fire.
- (b) Yes, with conditions: the run blocks the affected step and every step depending on it,
  continues independent work, records the decision prominently at the top of the PR body with
  options and a recommendation, never acts on an inferred answer, and the run is reported as
  partial rather than complete. Irreversible or Hard-Floor actions are excluded and keep their
  this-turn confirmation.
- (c) Another shape (state it).
