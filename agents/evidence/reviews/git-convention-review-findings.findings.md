| 1 | medium | src/scripts/sync_pr_branch.ts:737 | `--base refs/heads/<b>` is documented as "used as given", and `parseBaseRef`/`splitResolvedRef` (git_base_ref.ts:48) keep the ref as `refs/heads/<b>`. The behind count and the merge then run against the LOCAL branch, which `git fetch <remote> --prune` never updates. The strategy is read at the server SHA (`ls-remote origin refs/heads/<b>`). So one run judges the strategy at the server commit and the freshness at a clone-time local copy, and it can report "already current" against a stale base. git_base_ref.ts's own header names that stale copy as the reason bare names map to `origin/<b>`. The `uncountable` fetch hint also creates `refs/remotes/origin/<b>`, not the ref it counted. | open | |
| 2 | medium | src/scripts/check_branch_freshness.ts:284 | The base resolvers disagree again. `sync_pr_branch` (and `git:convention sync`) dropped the forge lookup and use the default branch when no `--base` is given. `check_branch_freshness` still asks the forge (`askForgeForBase`) for the PR base. On a PR into a non-default base, a caller that runs both without `--base` integrates one base and checks another. The two-resolver split is the defect git_base_ref.ts says it closes. taskfiles/dev.yml:209-210 says "the resolvers themselves never ask the forge", which is false for check_branch_freshness. | open | |

Before this change that run reached the fetch-failure path, which still exists and still returns exit 0 `unverified`. check_branch_freshness returns 0 NOT VERIFIED for the same condition. Now an unreachable remote is exit 1 or exit 0 depending on which network call fails first, and a repo that declares no strategy pays the network call and fails hard offline. | open | |
