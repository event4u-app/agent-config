# 6.0.0 — Validation gate + rollback criteria for the breaking change

> **Status:** Decided · 2026-06-02
> **Source:** road-to-6.0.0-a-positioning-and-validation roadmap (transient — `agents/roadmaps/`), Phase 0 / Steps 2–3
> **Decision record:** [`ADR-040`](../../../docs/decisions/ADR-040-execution-model-projection-time-filtering.md) (execution model)
> **Council:** claude-sonnet-4-5 + gpt-4o, 2026-06-02 — 2 rounds + peer-review; converged on "validation → positioning → projection → governance; front-load a validation gate because the rebuild rests on an N=1 external review (validator-capture risk)."

## Why this note exists

The 6.0.0 experience-first rebuild introduces a **breaking change**:
projection-time filtering (`ADR-040`) eventually narrows the projected artefact
set to the active profile + packs, instead of writing the full set. A breaking
change justified by a single external product review (N=1) is the council's
named top risk — **validator capture**. This note records the validation
evidence the change rests on, and the decision rule that keeps the change honest
about that evidence.

## Validation evidence (what justifies the breaking change)

| # | Evidence | Strength | Status |
|---|---|---|---|
| a | **Owner-intent** — the maintainer explicitly directed this rebuild. | Weak alone, but real and present. | ✅ Present (2026-06-02) |
| b | **Recruit-session gate** — the human-owner user-research session (the same gate `road-to-employee-product` Phase 1 has had blocked for months). | Strong when it runs. | ⏳ Blocked (human-owner; not autonomously runnable) |
| c | **Staged-rollout telemetry** — real usage signal once 6.0.0-B ships filtering as opt-in. | Strongest (real behaviour). | ⏳ Pending 6.0.0-B |

We do **not** pretend a 30-user study is autonomously runnable. Owner-intent (a)
is the minimum validation that lets 6.0.0-A proceed; (b) and (c) are the stronger
upgrades that gate the *default flip*, not the *mechanism*.

## Decision rule — staged rollout IS the validation mechanism

```
6.0.0-B ships projection filtering as OPT-IN (legacy-all is the default).
The default does NOT flip to filtered until recruit-session evidence (b) OR
staged-rollout telemetry (c) confirms the "too many surfaces" hypothesis.
Only THEN does 6.1.0 flip the default.
```

This converts the staged rollout itself into the validation mechanism, rather
than blocking 6.0.0 on a 30-user study that cannot run. The mechanism
(`ADR-040`) ships behind an opt-in flag; the behavioural default change is
evidence-gated.

## Rollback criteria (Step 3)

```
The 6.1.0 default-flip (legacy-all → filtered) REVERTS to legacy-all if the
post-flip support/issue signal spikes (regressions, "where did my command go?",
install-confusion tickets).
legacy-all is RETAINED — not removed — until filtered-mode usage proves it is
unneeded: < 10% of installs still on legacy-all.
```

Rollback is **evidence-based, not calendar-based**:

| Trigger | Threshold | Action |
|---|---|---|
| Post-flip support/issue spike | Sustained rise in "missing command/skill" or install-confusion reports after the 6.1.0 flip | Revert default to legacy-all; keep filtering opt-in |
| legacy-all retirement | < 10% of installs still selecting legacy-all | Safe to drop legacy-all in a later major |
| No signal either way | — | legacy-all stays; default stays whatever 6.1.0 set, pending more data |

- The **opt-in flag + filtered projection** is built in the 6.0.0-B roadmap.
