# 6.0.0 upgrade-cleanup (stale-file reaper) — verification record

Generated for `road-to-6.0.0-final-readiness` Phase 2. Records the
forward-upgrade and version-skew/staged scenarios exercised against the
stale-file reaper, the dry-run preview added in this phase, and the
documented version-skew behaviour. **Any scenario failure blocks 6.0.0**
(roadmap Phase 2 rollback).

## The reaper under test

`src/scripts/_lib/global_deploy_inventory.py` — two complementary paths,
both invoked from `install.py::_deploy_global_content` **after** the deploy
postcheck (a partial copy can never trigger deletions):

- **`reap_stale`** — diffs the previous per-tool inventory
  (`~/.event4u/agent-config/deployed-files.json`) against the current
  expected file set; deletes only previously-recorded, now-orphaned files.
- **`reap_tagged_orphans`** — runs on **every** deploy; deletes `.md` files
  carrying `package: event4u/agent-config` frontmatter that the current
  bundle no longer ships. This is the only path with ownership proof
  independent of inventory history.

Safety invariants (unchanged this phase, re-asserted by the test suite):
never deletes an unrecorded path, never outside the anchor, never a
directory, no-op when the inventory is missing/corrupt or the anchor moved.

## Dry-run added this phase

Both reaper functions gained `dry_run: bool = False`. With `dry_run=True`
they compute and return the would-delete set (only paths actually on disk)
**without unlinking or pruning**. `install.py --global --dry-run` now prints a
`reap (cleanup):` block listing exactly what a real deploy would remove —
satisfying "a dry-run that shows exactly what gets removed before any
deletion". The preview is computed read-only from the package source
(`expected_deploy_files`, no copy) + the on-disk anchor + inventory, so it is
exact: **dry-run set == live-delete set** (proven by
`test_dry_run_set_equals_live_delete_set`).

Live smoke (this machine, `--tools=claude-code`): the preview listed 4 real
pre-existing orphans in `~/.claude/commands/` (chat-history/{learn,show},
fix/{pr-bot-comments,pr-developer-comments} — genuine pre-merge leftovers) and
a planted `__ac_phantom_orphan__` skill, deleting nothing. Confirmed the
planted file survived the dry-run.

## Version-skew / staged scenarios — behaviour + results

The version gate lives in `install.py` (`install_global`, the
`classification == "downgrade" and not force: return 1` check at line ~3551)
**before** `_deploy_global_content` (line ~3600). So the reaper is structurally
gated behind the version check: a refused install never reaches it.

| # | Scenario | Documented behaviour | Verified by |
|---|---|---|---|
| V1 | 6.0.0 global + 5.10.1 project coexistence | The global lockfile (`~/.event4u/agent-config/installed.lock`) governs global-anchor deploys; a project install writes its own project-local layer. They do not contend for the same files — global anchors vs project `.agent-settings.yml`/`.augment`. No silent cross-scope clobber. | install.py scope separation; settings-migration tests |
| V2 | 6.0.0 → 5.10.1 downgrade (ghost resurrection?) | Refused unless `--force` (`classification == "downgrade"` → `return 1`), so no reaping occurs on a plain downgrade. With `--force`, re-deploying the older bundle re-creates only what that bundle ships; a file absent from **both** bundles never resurrects. | N2 trace (gate precedes deploy) + `test_downgrade_reaped_files_do_not_resurrect` |
| V3 | Lock-file version mismatch | Recorded-lower (or unparseable) = upgrade → auto-heal, claim the new version slot, proceed (kills the silent-refusal trap). Recorded-higher = downgrade → refuse unless `--force`. The lockfile claims the new version **before** the deploy so a mid-deploy failure retries cleanly. | `install.py` lines ~3540–3600; `test_check_lockfile_freshness_drift` |
| V4 | Partial / staged upgrade (global on 6.0.0, a project/tool migrated later) | The tag sweep runs on **every** deploy regardless of inventory history, so a tool deployed for the first time after the global upgrade still gets its pre-existing tagged orphans cleaned. | `test_staged_upgrade_late_tool_still_cleaned` |

## No-ghost-files conclusion

Every forward scenario leaves no package-tagged orphan behind (the tag sweep
is idempotent: a clean tree yields zero deletions —
`test_reap_tagged_orphans_is_idempotent`,
`test_deploy_real_bundle_reaps_planted_orphan_and_is_idempotent`). The dry-run
output lists the exact to-be-removed set before any deletion. Version-skew
behaviour is documented above and gated so deletions never occur on a refused
install. **No scenario failed → Phase 2 does not block 6.0.0.**
