## How pre-registered this registration actually is — the honest limit

Two readings were seen before this file was written, and they are **anchors,
not results**: the roadmap's F9 survival check (bracket form fails three of four
surfaces; three other spellings survive all four) and its F3 census (the tree's
own phone and card regexes over 12,729 tracked text files: 32,743 phone hits,
393 card hits, 49 Luhn-valid). Neither is a measurement of the engine this
roadmap builds, and no bar below is a threshold placed near either number. No
model-fidelity, recall, precision, quality or latency reading of any kind
existed when this was committed.

## Corpus — four workloads, frozen before the first scored run

| Workload | Content | Purpose |
|---|---|---|
| W1 identifier-heavy prose | support threads, invoices, CRM notes with synthetic e-mail, phone, IBAN, card and tax-ID values | recall per identifier type |
| W2 credential-heavy configuration | `.env`, YAML, JSON, shell profiles with synthetic keys, tokens, passwords, connection strings | recall per credential type |
| W3 implicit identity | prose that identifies a person or customer with no listed span | **reported, not passed** — the size of the implicit-identity residue |
| W4 proprietary code | this repository's tracked text files plus a labelled negative corpus (fixture addresses, commit identities, card-shaped test numbers, hashes, UUIDs) | precision |

Every planted value is synthetic and generated by a fixed seed; no real
identifier enters the corpus. The corpus lives under `tests/fixtures/` and is
frozen at the commit that first scores it; a later change to it is a new
registration.

## Endpoints and bars

Each bar is derived from a principle that does not reference an observed value,
and each names its null.

### (a) Recall per class

**Bar: ≥ 99% recall for e-mail and for checksum-valid IBAN on W1; ≥ 99% recall
for every credential type the rule table lists on W2.**
*Derivation.* These types have a closed, validatable shape; a miss rate above
one in a hundred on synthetic, well-formed values is a rule defect, not
ambiguity. Phone, card and tax ID are reported per type with no pass bar: their
rules require a context word by design, so their recall is a property of the
corpus's phrasing as much as of the rule.
*Null.* Any listed type below its bar fails the endpoint; the result is
published per type, and that type's channel cannot leave `uncovered` on its
strength.

### (b) Precision on code

**Bar: false positives under 1% of files on W4, and zero on the labelled
negative corpus for e-mail and IBAN.**
*Derivation.* A replacement that fires on ordinary code damages what a reviewer
reads (risk 1 of the roadmap); a validated type that fires on a known-benign
fixture is a validator defect.
*Null.* Above the bar, replacement for that type stays behind `mode: off` for
every consumer regardless of the D8 answer.

### (c) Byte-exact round trip

**Bar: zero tolerance. For every W1/W2 document, `restore(replace(x)) == x`
byte for byte for identifiers, and `replace(replace(x)) == replace(x)`.**
*Derivation.* A round trip that alters bytes is not a restore; idempotence is
what makes a token never match a rule.
*Null.* One mismatch fails the endpoint.

### (d) Model fidelity per token spelling — settles D3

**Candidates, frozen:**

| ID | Spelling (IBAN, number 1, fingerprint `495cff`) |
|---|---|
| S1 | `⟦IBAN_1.495cff⟧` |
| S2 | `__IBAN_1_495cff__` |
| S3 | `__AC_IBAN_1_495cff__` |

These are the three F9 survivors with the fingerprint 3.1 requires added in the
same position for all three; the bracket form `[IBAN_1]` is excluded by F9.

**Protocol.** The host model is given a short context containing tokens of one
spelling and a task that requires a tool call whose input must contain a token
(write a file holding the value, run a command naming it, call a tool with it).
The tool call is captured from the host's structured output and **not
executed**. Trials: five types (`EMAIL`, `PHONE`, `IBAN`, `CARD`, `APIKEY`) ×
four task templates = 20 per spelling, identical across spellings except for the
spelling. Seat: the Claude Code host model through `claude -p`, run from a
directory outside any repository so no project rules load. A second provider is
reported if its CLI exposes tool-call inputs; if not, that is stated, not
inferred.

**Score.** Fidelity = trials in which every expected token appears in the tool
input byte-identical ÷ trials. A trial with no tool call is scored as a failure,
not dropped.

**Bar: fidelity = 20/20 for a spelling to pass.** *Derivation.* A token that
comes back altered resolves to nothing (or to the wrong value under a lax
recogniser); at this sample size the only defensible bar is no observed
corruption. The honest limit: 20/20 bounds the true failure rate below roughly
14% at 95% confidence, so this bar separates "copies reliably" from "visibly
corrupts", nothing finer.

**Selection rule, fixed now.** Among passing spellings, prefer ASCII-only over
non-ASCII (fewer encoding surfaces); among ASCII-only, prefer the shorter. The
selected spelling becomes the one grammar constant of step 3.1.

*Null.* No spelling passes → 3.1 does not land; D3's revisit trigger fires and
the result is published.

### (e) Paired task quality

**Bar: no regression beyond the paired verdict's own noise floor** on a task set
drawn from council reviews and coding tasks with and without replacement, scored
through `src/scripts/_lib/paired_verdict.ts`. *Null.* A loss is published, and
D8 keeps consumer defaults `off`.

### (f) Engine latency, apart from any gateway

**Bar: p95 under 20 ms per request-sized input (64 KiB) on the CI runner class.**
*Derivation.* A starting proposal from the roadmap, kept as stated rather than
tuned; the hook-latency trigger already fired, so the engine must not be the
reason a hook slows. *Null.* Above the bar, no hook carrier may call the engine
synchronously.

## Falsification

Each endpoint's scorer must first reject a planted defect before its green
reading counts: a rule with its IBAN checksum disabled for (a)/(b), a restore
that drops one byte for (c), a fidelity scorer fed a deliberately altered token
for (d).
