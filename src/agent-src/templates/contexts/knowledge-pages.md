# Knowledge Pages — lifecycle-typed sibling directories

Templates for the four typed directories added beside the existing
anti-hallucination knowledge cards (`agents/knowledge/<source>.md`,
[`knowledge-card.md`](knowledge-card.md)). **Existing cards are untouched by
this template** — this is a sibling addition, not a migration.

## The four directories

| Directory | Lifecycle stage | Holds |
|---|---|---|
| `agents/knowledge/sessions/` | Episodic | What happened — consolidated session learnings, one file per topic or date |
| `agents/knowledge/concepts/` | Semantic | What is true — project facts: coding standards, module structure, API shapes, domain terms |
| `agents/knowledge/procedures/` | Procedural | How to — step-by-step knowledge on its way to becoming a skill (`skill-candidates.md` lives here) |
| `agents/knowledge/decisions/` | Decision record | Small decisions not big enough for a full ADR |

`agents/knowledge/INDEX.md` catalogs all five surfaces (cards + the four
directories) with one line per page — generated by
`src/scripts/generate_knowledge_index.ts`. **Retrieval protocol: read the
index first, `grep` for keywords second, read the specific file third.**
Never enumerate every knowledge file directly; there is no search
infrastructure by design — index-first + grep only.

## Storage location IS the sharing policy

Personal, cross-project knowledge belongs in the ADR-100 user-global store
(`~/.event4u/agent-config/knowledge/`, via `knowledge_global_cli.ts`) —
never in these project-local directories. Team knowledge belongs here, in
the consumer repo, so the whole team benefits from it via git. Promotion
from project-local to global requires cross-project evidence and goes
through the existing manual global-store promotion path — never automatic.

## Entry micro-schema — `date + what + why`

Every page entry (especially in `sessions/`) states, at minimum:

```markdown
- 2026-07-05: <what happened / was learned> — <why it matters>
```

Keep entries short. Longer explanation belongs in the page body below the
entry list, not stuffed into one line.

## Page frontmatter — optional, warn-linted only (v1)

None of these fields are mandatory in v1 (schema-as-contract is explicitly
deferred until real team usage data exists). When present, they are
warn-linted for shape only:

```yaml
---
type: concept            # concept | procedure | session | decision
scope: project            # user | project | global
visibility: team           # private | project | team
review_after: "YYYY-MM-DD" # optional scheduled re-check date
contested: []              # append-only array — see "Contested entries" below
---
```

## Contested entries — never silently resolved

When a live contradiction is found between documented and observed
reality, the page gets an **append-only** `contested:` entry instead of a
silent rewrite:

```yaml
contested:
  - timestamp: "2026-07-15T14:23:11Z"
    trigger: context_stale
    evidence: "profile.test.ts:45 expected {success, payload}"
    session: "<session id or chat-history pointer>"
```

Resolution is always human — either via the `team-knowledge:consolidate`
gate, or via an isolated, this-turn-approved fix commit. A page carrying
≥2 unresolved `contested` entries is flagged by the knowledge lint for
consolidation attention.

## Page size budget

Keep pages ≤ 200 lines. Split by sub-topic before that limit — a
too-broad page defeats index-first scanning just as much as too many
tiny pages do.
