# Retrieval read surfaces — where the sanitize floor is in scope

The coverage list for `src/scripts/_lib/retrieval_sanitize.ts`.

It used to live in that module's header as prose, and it was wrong in both
directions when it was last read against the tree: a path that reaches the
outside world and **is** sanitized was absent from it, and two paths carrying
fetched bytes toward a model-facing surface were neither listed nor covered.
The version before that had already recorded the same failure once, in its own
words — it "named surfaces by intent, and the legacy-envelope gap went
unnoticed for exactly that reason".

So the list is no longer written. `src/scripts/_lib/read_surface_scan.ts`
derives it from the import graph, `check_read_surface_coverage` regenerates the
table below and fails when the committed copy and the tree disagree, and the
module header now carries a pointer here instead of a second copy — which the
same gate also enforces, because two copies is how the list went stale twice.

## Reading a row

- **inbound shape** — how outside bytes enter. `network-fetch` · `node-http-request`
  · `remote-subprocess` · `stdin-markup-parse` · a shape the module declares at
  its own site with `// read-surface: <id>`, for a channel no call site spells
  (a host subagent reply, an ingested corpus read from disk).
- **emit shape** — how the module hands a string onward, or `undecided`.
- **coverage** — `covered` when the module imports the floor, `uncovered` when it
  does not, `unclassified` when the scanner cannot decide.

`unclassified` is the row type that matters. A generated table carries an
authority a hand-written one never claimed, so its worst failure is not a wrong
row but an **absent** one: a network call reached through an injected callee
produces no strong match, and silence reads as "no surface here". Those get a
row anyway, marked `unclassified`, so an unrecognised shape appears as a visible
gap.

**A row is a claim about imports, not about safety.** `covered` means the
module imports the sanitize floor, so the floor is in scope there. It does
not say the floor is applied to the right string or at the right point —
that needs a read of the module, and no import graph can supply it.

**What is out of scope, said here rather than left to be discovered.** a `git` subprocess reads local repository state, not outside bytes, so it is not an inbound shape. `git fetch` and `git ls-remote` move refs rather than content and are excluded with the rest — a branch name is attacker-influenceable in principle, and if that ever reaches a model-facing surface it needs its own row, not a widened matcher that would re-add every local `git status` wrapper in the tree.
